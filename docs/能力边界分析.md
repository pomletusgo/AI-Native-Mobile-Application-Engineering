本文件是任务 6.2「汇总 OCR 与字段抽取的错误原因与能力边界分析」的交付物。

写作口径与 `docs/验证报告.md` 一致：**只写代码里确实存在的规则与确实执行过的检查**。凡是还没有真实名片照片 / 真实 OCR 原文支撑的结论，一律标注为「待执行」，不用估计值充当结果。概率性功能（检测、OCR、字段抽取）不判定「通过 / 失败」，而以 `testcards/ground_truth.json` 的字段级准确率与缺失字段误报率度量（见 `docs/规格说明书.md` 3.3 与 7.2）。

## 1. 分析对象与证据口径


## 2. OCR 层的错误原因

### 2.1 输入侧

| 原因 | 说明 | 位置 |
| --- | --- | --- |
| 图像方向 | 校正只做透视摆正、不转 90°，方向完全依赖拍摄 / 导入阶段给的信息。若方向元数据缺失或与实际不符，识别质量整体下降 | `VisionCardBoundaryDetector.correct`（不做 90° 旋转） |
| 只取首帧 | 解码用 `CGImageSourceCreateImageAtIndex(source, 0, nil)`，多图 / 多帧图像源只用第一帧 | `VisionOCRService.recognize` |
| 无图像预处理 | 不做二值化、去背景、对比度增强、放大。低对比度（深色底浅字、照片偏暗）与复杂 Logo / 底纹背景都会掉字，也解释了数据集里 `darkBg` / `complexBg` / `shadow` 这几类质量标注的意义 | `VisionOCRService.recognize` 直接把原图交给 Vision |
| 上游框偏差 | 识别对象是校正后的图。框选偏（自动检测误检，或手动调整没对齐卡片边缘）会把背景文字一起带进来，成为后续字段抽取的噪声源 | 由 §4 的检测层决定 |

### 2.2 引擎侧

| 原因 | 说明 | 位置 |
| --- | --- | --- |
| 语言集固定 | 只声明 `zh-Hans` 与 `en-US`。繁体中文、日文、韩文等不在列表内，识别质量无保证 | `VisionOCRService.init` 默认参数 |
| 语言纠正在起作用 | `usesLanguageCorrection = true` 会用语言模型修正识别结果。好处是常见词更准，代价是会把数字与专有名词「纠」成字词，例如邮箱里的 `0` / `O`、`1` / `l` 被互换——这类错误肉眼不易发现，且会直接传给字段抽取 | `VisionOCRService.recognize` |
| 只取首个候选 | 用 `observation.topCandidates(1).first`，**不看置信度、不做阈值过滤**：识别得很勉强的字符也照样进入结果，没有「低置信 → 提示人工重点核对」这条路径 | `VisionOCRService.recognize` |
| 识别级别 | 固定 `.accurate`。无速度 / 精度的取舍开关，长耗时场景（大图）只能整体等待 | `VisionOCRService.init` 默认参数 |

### 2.3 版式侧

阅读顺序由 `sortedInReadingOrder()` 决定：先按 `midY` 自上而下，同一行的判定依据是**相邻块纵向重叠**，容忍度为 `max(两个块的高度) × 0.6`，行内再按 `minX` 从左到右。

- 斜排文字、竖排文字、艺术字：Vision 给出的包围盒本身就不规则，分行与排序都可能错，进而让「标签: 值」被拆到不同段。
- 并排多列版式（左右两栏）：同一条水平带上的两个不同栏位会被并成一行，行内顺序按 `minX`，可能造成字段归属错位。
- 容忍度是固定比例（0.6）而非自适应聚类，行距特别密或字号差异特别大的版式容易出现「该分行却并了行」。

以上三点均为**规则层面的推断**（可由代码直接坐实），真实名片上的表现需在数据集上统计（§6）。

### 2.4 失败与错误类型

| 错误 | 触发条件 | 语义 |
| --- | --- | --- |
| `OCRError.invalidImageData` | 数据无法解码成图像 | 提示重拍或重选图片 |
| `OCRError.noTextFound` | 图像可读但没有任何文字 | **按失败处理**，不返回空结果——对应「不得保存空名片」 |
| `OCRError.failed(reason:)` | 引擎本身报错 | 把引擎的 `localizedDescription` 透出 |

边界：`noTextFound` 是「一个字都没有」才算失败。**识别出错字不算失败**——只要有文本，就会继续走到字段抽取，错字由用户在校对页改正。这是本工程的既定取舍，不设自动置信度告警。

## 3. 字段抽取层的错误原因

`BusinessCardFieldParser` 是规则抽取器：把文本切成段（先按行，再按 2 个以上空白，再按中英书写系统交界，最后拆出段首 / 段尾的职位词），逐段按固定顺序判定，**先命中者先占位、已有值的字段不会被覆盖**。判定顺序见 `BusinessCardFieldParser` 的类型注释：Email → 网址 →「标签: 值」→ 邮编 → 电话 → 地址（强特征）→ 公司 → 地址（弱特征）→ 部门 → 职位 → 姓名。

### 3.1 共性原因

| 原因 | 后果 |
| --- | --- |
| 词表驱动 | 机构、职位、部门、地址的判定全靠关键词表。表外的写法（自造词、缩写、外文机构名）要么落到后面的分支、要么整段丢弃 |
| 顺序敏感 | 公司排在职位与姓名之前、地址强特征排在公司之前。同一段文本同时含多类特征时，结果由顺序决定，不由「哪个更像」决定 |
| 只取首个候选 | 同一字段出现多个候选时，其余全部丢弃（对应测试 `testOnlyFirstCandidatePerFieldIsKept`），多余信息既不入库也不提示 |
| 归一化范围有限 | 全角转半角只覆盖数字、字母与 `:` `／` `.`；全角括号等符号保持原样，会让含它们的号码判定失败（§3.5） |
| 不产出推测值 | 判定不了就丢弃，`name` 没有候选时保持 `nil`（不用公司名顶替，测试 `testCompanyOnlyCardHasNoNameAndCannotBecomeCard`） |

### 3.2 姓名

规则：不含数字；中文 2–4 个汉字，或 2–4 个西文词且每词首字母大写、词内不含连续大写（排除全大写缩写）。

- **漏抽**：单个西文名（`Cher`）不判姓名；超过 4 个汉字的姓名（复姓加少数民族长名）不判姓名；全部大写的西文名（`ZHANG WEI`）被「无连续大写」规则排除。
- **误报**：不含任何机构后缀的 3–4 字机构简称（如「国泰君安」这类不在 `companySuffixes` 里的写法）会一路落到最后一步被判为姓名。「星辉传媒」之所以不误判，是因为 `传媒` 在机构后缀表内（测试 `testCompanyOnlyCardHasNoNameAndCannotBecomeCard`）。
- **同行合并**：姓名与机构写在同一行、中间只有**一个**空格时不会被切开（切分只按 2 个以上空白或中英交界），整段会因含机构后缀而被判为公司，姓名漏抽。

### 3.3 公司

规则：段内含 `companySuffixes` / `latinCompanySuffixes` 中任一片段即判机构（中文含 `有限公司` / `集团` / `大学` / `科技` 等，西文含 `inc` / `ltd` / `technologies` / `consulting` 等）。

- **漏抽**：无上述后缀的机构名（如 `Acme`、纯自造词品牌）不判公司。
- **误报**：词表按子串匹配，长词里的片段会命中。代码已刻意避开已知冲突（不收 `co`——它会命中 `Consulting`；不收 `tech`——会命中 `Technical Director`；行业词表不收与职称重叠的 `设计` / `网络`），但这只是逐个排除，新写法仍可能撞上。
- **顺序副作用**：公司判定早于部门与职位，含机构后缀的部门名（如「XX 大学研发部」）会先被占成公司。

### 3.4 职位与部门

- 职位靠关键词（中文 21 个如 `总经理` / `工程师` / `合伙人`，西文 24 个如 `director` / `engineer` / `architect`）子串命中；表外职称（`Chief of Staff`、`LEAD`）漏抽。
- 段首西文职位词会被拆出来单独判定（`Professor Tongji University` → `Professor` + `Tongji University`），**段尾**的多词短语整体保留，靠整段命中关键词入选。
- 部门词表含单字 `部` / `处` / `科` / `系`，命中面很宽：含这些字的**地址**（如「解放路 3 号 2 处」）在顺序上已先被强地址特征（路 / 号）占走，但不含强地址特征时可能被误判成部门。

### 3.5 电话三型（手机 / 固话 / 传真）

规则：值必须「只由数字与 `+ - ( ) . / ·` 与空格组成、数字 7–15 位」。有标签按标签归属；无标签时按启发式定类型：`+86` 且 ≥13 位 → 手机，以 `0` 开头 → 固话，≥11 位 → 手机，**其余一律落手机**。

- **误报**：无标签的传真号（如「021-6000-3001」单独一行）会因 `0` 开头被判固话；无标签且判不出类型时统一落手机，可能把固话写进 `mobile`。
- **漏抽**：全角括号（`（021）…`）不在允许的分隔符内，而归一化不转全角括号，整段判定失败、号码丢失；带分机号（`转 8021`）或含汉字的号码行同样失败。
- **归属冲突**：同一张名片两个手机号时，第二个既不能进 `mobile`（已被占），也不会进 `phone`（有标签时按标签走，无标签时首个候选先占），只能靠人工在校对页补。

### 3.6 邮箱

- 正则 `[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}`：段内含匹配子串即抽该子串，因此「邮箱和其它文字同行」也能抽出。
- 边界：中文域名邮箱、TLD 为单字符的邮箱不匹配；OCR 把 `@` 认成 `(a)` 或把字母认错时无法修复（这一层不做纠错）。

### 3.7 网址

规则：带 `http(s)://` 或 `www.` 前缀直接认定；否则必须**整段就是域名**（无空格 / 冒号 / 斜杠，且顶级域在 13 个已知 TLD 内）。

- **漏抽**：未知 TLD（`.xyz`、`.tech` 等）不判网址；无协议的带路径写法（`example.com/about`）因含斜杠不判；带标签的整行（`网址:http://a.com`）走标签分支，能正常归属（测试 `testLabeledWebsiteLineIsNotTreatedAsUrl`）。
- **不误报**：段内含 `@` 时直接返回 `nil`，避免把邮箱当网址；`Apple` 这类单词不含点，也不判网址。

### 3.8 地址与邮编

- 地址：强特征（`路` / `街` / `号` / `楼` / `室` / 大厦 / 广场 / `street` / `suite`…）与弱特征（`省` / `市` / `区` / `县` / `district` / `city`…）两级词表，只抽第一段命中的，**不做多行地址合并**——分两行写的地址只留下第一行。
- 邮编：只认**整段就是 6 位数字**。「邮编：430074」走标签分支可抽出；写进地址行中间（「…大道 100 号 430074」）不会被抽出，会被整段判成地址。

### 3.9 与规格 4.3 的偏差（需如实记录）

| 规格 4.3 的要求 | 当前实现 | 状态 |
| --- | --- | --- |
| 字段歧义（如 `Apple`）：无法确定则 `nil`，不得多字段重复填充 | 单西文词既不判姓名也不判公司，保持 `nil` | 符合 |
| 人名 vs 公司：禁止把公司名识别为姓名 | 机构后缀优先于姓名判定 | 基本符合，但见 §3.2 的「无后缀机构简称」风险 |
| 多电话必须区分 Mobile / Office / Fax | 有标签时按标签归属；无标签时用启发式 | 符合，标签缺失时可能误归（§3.5） |
| **多 Email：主邮箱入 `email`，其余进入 `notes` 或保留列表** | 只保留第一个，其余**丢弃**；`BusinessCard.notes` 字段存在但抽取器从不写入 | **未实现**（规格标注为「Week4 细化」） |
| 中英混排：姓名保留原语言、不翻译 | 保持原文（测试 `testBilingualNameKeepsOriginalLanguage`） | 符合 |
| 字段缺失：返回 `nil`，禁止补全 | 硬约束，由 `makeCard()` 与误报率指标共同守住 | 符合 |

## 4. 检测与校正层对 OCR 的上游影响

这几条严格说属 T06 能力，但它们的误差会直接变成 OCR 的输入误差，故一并汇总：

- **只检矩形**：`VNDetectRectanglesRequest`（`minimumAspectRatio` 0.3、`minimumSize` 0.18、`quadratureTolerance` 30、`maximumObservations` 4、`minimumConfidence` 0.5）。弯曲、被手指遮挡、倾斜过大、白底白桌上的名片可能直接 `notFound`。
- **取面积最大者**：多个候选中挑面积最大的一个。画面里存在更大的矩形（桌面边缘、显示器、另一张纸）时会选错，而选错后走的是「检测成功」路径，不会提醒用户。
- **`isReliable()` 阈值是初值**：面积 `0.12…0.98`、长宽比 `1.15…3.6`，**尚未在真实照片上标定**。阈值偏严会把正常名片判成「不可靠」（多走一次手动调整），偏松会把桌面误检当名片放过去。
- **不自动转 90°**：竖版名片合法，仅凭四边形比例无法区分「竖版名片」与「照片方向不对」，误转会破坏识别；因此方向问题被推给上游，识别不理想时靠重拍或手动调整。
- **手动调整的取舍**：用户手动改框时**豁免**自动检测的最小面积（0.12）与长宽比启发式（用户已看过照片并自己指出名片位置，再用同一套启发式拒一次会让该功能形同虚设），但**保留面积上限 0.98**，守住规格「不直接把整张图片当作名片」。

## 5. 已明确不做（能力之外）

对齐 `docs/规格说明书.md` 2.2 与作业文档第十五节，以下不在本次复刻范围，也不在本文的能力边界讨论范围内：用户注册 / 会员 / 订阅支付 / 广告、云同步与多设备同步、团队名片库与 CRM（Salesforce）同步、企业权限与组织、数字名片设计 / 模板、QR 名片交换、Email Signature、AI 企业情报 / 公司分析、会议录音与总结、销售漏斗。

在**本工程范围之内**但明确不做的还有：

- 云 OCR / 第三方 OCR 服务：只用端上 Vision。
- 手写体识别、竖排中文专门处理、名片 Logo 与版式的语义理解。
- OCR 结果的自动纠错与置信度告警：识别错字只能由用户在校对页改正。
- 多语言（简体中文与英文之外）识别与翻译。
- 图像预处理增强（去噪、去背景、锐化、透视之外的方向校正）。

## 6. 如何把上述边界量化（任务 4.4，待执行）

### 6.1 指标定义（脚本已实现）

`CamCardCloneTests/FieldExtractionEvaluator.swift` 对 `BusinessCardFieldParser` 在 OCR 原文上的输出与 `testcards/ground_truth.json` 比对，输出：

- **字段级准确率** = 判定正确字段数 / 参与评价字段数；
- **缺失字段误报率** = 本应为空却抽出值的字段数 / 本应为空的字段数（量化「不得虚构」，理想值为 0）；
- 逐字段的正确 / 参与数与**错误明细表**（名片 ID、字段、判定、真值、抽取结果），用于定位是哪些字段在拉低准确率。

判定分五种：`correct` / `mismatch`（抽成了别的）/ `missed`（漏抽）/ `invented`（虚构）/ `absent`（本应为空且确实为空）。比对前做既定的等价归一化：去首尾空白、压缩内部空白、忽略大小写；电话类字段再忽略分隔符（`138-0000-0001` 与 `13800000001` 视为相同）。参与评价的字段为 9 个：姓名 / 公司 / 职位 / 手机 / 固话 / 传真 / 邮箱 / 网站 / 地址——**邮编与部门不在评价范围内**，数据集里的 `additionalEmails` 也不参与评价（评价键取自 `groundTruth` 与 `expectedAbsent`）。

### 6.2 数据缺口与执行步骤

缺口有两处，且都必须先补齐才能给出数字：

1. **缺 OCR 原文**：约定路径 `testcards/ocr/<卡片ID>.txt` 尚未产出；
2. **缺名片图片**：`testcards/ground_truth.json` 只有 30 张卡的字段真值，没有与之对应的名片图片，因此无法在端上跑出 OCR 原文。

执行步骤（拿到 Mac 后）：

1. 用真实名片照片走一遍 App 的识别链路（`docs/UI验收清单.md` M18），或在模拟器 / 真机上对合成名片图片调用 `VisionOCRService`；
2. 把每张卡片的 OCR 原文按 `<卡片ID>.txt` 写入 `testcards/ocr/`；
3. 运行 `testFieldAccuracyOnCorpusIsPendingUntilOCRTextsExist`（当前以 `XCTSkip` 退出，目录出现后自动改为真实断言），由 `FieldExtractionEvaluator.report` 生成准确率、误报率与错误明细；
4. 按错误明细回填本文 §3 各字段的「真实数据下的表现」，把推断换成实测。

### 6.3 `isReliable()` 阈值标定

在真实照片上分别统计「正确框选」「误检桌面 / 屏幕」「漏检」三类样本的面积与长宽比分布，再据此收紧或放宽 `0.12` / `0.98` / `1.15…3.6`，并在 `docs/验证报告.md` 与 `docs/规格测试追踪表.md` 的 T06 行更新结论。标定完成前，这三个数字都只能算初值。
