### 1. 分析对象与证据口径

链路（`docs/规格说明书.md` 2.1 的核心闭环）：

```
CardBoundaryDetecting.detectCard（区域检测）
  → CardBoundaryCorrecting.correctCard（透视校正）
  → OCRService.recognizeText（文字识别）
  → BusinessCardFieldParser.parse（字段抽取）
```

### 2. OCR 层的错误原因

#### 2.1 输入侧

| 原因 | 说明 | 位置 |
| --- | --- | --- |
| 图像方向 | 校正只做透视摆正、不转 90°，方向完全依赖拍摄 / 导入阶段给的信息。若方向元数据缺失或与实际不符，识别质量整体下降 | `VisionCardBoundaryDetector.correct`（不做 90° 旋转） |
| 只取首帧 | 解码用 `CGImageSourceCreateImageAtIndex(source, 0, nil)`，多图 / 多帧图像源只用第一帧 | `VisionOCRService.recognize` |
| 无图像预处理 | 不做二值化、去背景、对比度增强、放大。低对比度（深色底浅字、照片偏暗）与复杂 Logo / 底纹背景都会掉字，也解释了数据集里 `darkBg` / `complexBg` / `shadow` 这几类质量标注的意义 | `VisionOCRService.recognize` 直接把原图交给 Vision |
| 上游框偏差 | 识别对象是校正后的图。框选偏（自动检测误检，或手动调整没对齐卡片边缘）会把背景文字一起带进来，成为后续字段抽取的噪声源 | 由 §4 的检测层决定 |

#### 2.2 引擎侧

| 原因 | 说明 | 位置 |
| --- | --- | --- |
| 语言集固定 | 只声明 `zh-Hans` 与 `en-US`。繁体中文、日文、韩文等不在列表内，识别质量无保证 | `VisionOCRService.init` 默认参数 |
| 语言纠正在起作用 | `usesLanguageCorrection = true` 会用语言模型修正识别结果。好处是常见词更准，代价是会把数字与专有名词「纠」成字词，例如邮箱里的 `0` / `O`、`1` / `l` 被互换——这类错误肉眼不易发现，且会直接传给字段抽取 | `VisionOCRService.recognize` |
| 只取首个候选 | 用 `observation.topCandidates(1).first`，**不看置信度、不做阈值过滤**：识别得很勉强的字符也照样进入结果，没有「低置信 → 提示人工重点核对」这条路径 | `VisionOCRService.recognize` |
| 识别级别 | 固定 `.accurate`。无速度 / 精度的取舍开关，长耗时场景（大图）只能整体等待 | `VisionOCRService.init` 默认参数 |

#### 2.3 版式侧

阅读顺序由 `sortedInReadingOrder()` 决定：先按 `midY` 自上而下，同一行的判定依据是**相邻块纵向重叠**，容忍度为 `max(两个块的高度) × 0.6`，行内再按 `minX` 从左到右。

- 斜排文字、竖排文字、艺术字：Vision 给出的包围盒本身就不规则，分行与排序都可能错，进而让「标签: 值」被拆到不同段。
- 并排多列版式（左右两栏）：同一条水平带上的两个不同栏位会被并成一行，行内顺序按 `minX`，可能造成字段归属错位。
- 容忍度是固定比例（0.6）而非自适应聚类，行距特别密或字号差异特别大的版式容易出现「该分行却并了行」。

以上三点均为**规则层面的推断**（可由代码直接坐实），真实名片上的表现需在数据集上统计（§6）。

#### 2.4 失败与错误类型

| 错误 | 触发条件 | 语义 |
| --- | --- | --- |
| `OCRError.invalidImageData` | 数据无法解码成图像 | 提示重拍或重选图片 |
| `OCRError.noTextFound` | 图像可读但没有任何文字 | **按失败处理**，不返回空结果——对应「不得保存空名片」 |
| `OCRError.failed(reason:)` | 引擎本身报错 | 把引擎的 `localizedDescription` 透出 |

边界：`noTextFound` 是「一个字都没有」才算失败。**识别出错字不算失败**——只要有文本，就会继续走到字段抽取，错字由用户在校对页改正。这是本工程的既定取舍，不设自动置信度告警。

### 3. 字段抽取层的错误原因

`BusinessCardFieldParser` 是规则抽取器：把文本切成段（先按行，再按 2 个以上空白，再按中英书写系统交界，最后拆出段首 / 段尾的职位词），逐段按固定顺序判定，**先命中者先占位、已有值的字段不会被覆盖**。判定顺序见 `BusinessCardFieldParser` 的类型注释：Email → 网址 →「标签: 值」→ 邮编 → 电话 → **职位** → **地址 / 公司（特征竞争）** → 部门 → 姓名（2026-11-02 的 `fix-field-classification-errors` 变更把职位提到地址 / 公司之前、并把地址与公司改为共用一段特征竞争，见 §3.3 / §3.4）。

#### 3.1 共性原因

| 原因 | 后果 |
| --- | --- |
| 词表驱动 | 机构、职位、部门、地址的判定全靠关键词表。表外的写法（自造词、缩写、外文机构名）要么落到后面的分支、要么整段丢弃 |
| 顺序敏感 | 公司排在职位与姓名之前、地址强特征排在公司之前。同一段文本同时含多类特征时，结果由顺序决定，不由「哪个更像」决定 |
| 只取首个候选 | 同一字段出现多个候选时，其余全部丢弃（对应测试 `testOnlyFirstCandidatePerFieldIsKept`），多余信息既不入库也不提示 |
| 归一化范围有限 | 全角转半角只覆盖数字、字母与 `:` `／` `.`；全角括号等符号保持原样，会让含它们的号码判定失败（§3.5） |
| 不产出推测值 | 判定不了就丢弃，`name` 没有候选时保持 `nil`（不用公司名顶替，测试 `testCompanyOnlyCardHasNoNameAndCannotBecomeCard`） |

#### 3.2 姓名

规则：不含数字；中文 2–4 个汉字，或 2–4 个西文词且每词首字母大写、词内不含连续大写（排除全大写缩写）。

- **漏抽**：单个西文名（`Cher`）不判姓名；超过 4 个汉字的姓名（复姓加少数民族长名）不判姓名；全部大写的西文名（`ZHANG WEI`）被「无连续大写」规则排除。
- **误报**：不含任何机构后缀的 3–4 字机构简称（如「国泰君安」这类不在 `companySuffixes` 里的写法）会一路落到最后一步被判为姓名。「星辉传媒」之所以不误判，是因为 `传媒` 在机构后缀表内（测试 `testCompanyOnlyCardHasNoNameAndCannotBecomeCard`）。
- **同行合并**：姓名与机构写在同一行、中间只有**一个**空格时不会被切开（切分只按 2 个以上空白或中英交界），整段会因含机构后缀而被判为公司，姓名漏抽。

#### 3.3 公司

规则（2026-11-02 起）：地址与公司共用一段**特征竞争**（`addressOrCompanyKey(for:)`）——段内出现**门牌号类数字**（`hasStreetNumberEvidence`）或**行政区划词**（`hasAdministrativeDivision`）→ 判地址；**公司后缀位于段尾**（`hasCompanySuffixAtTail`）→ 判公司；两者都无证据 → **不下判**（返回 `nil`），继续下渗到部门 / 姓名。西文机构后缀表含 `inc` / `ltd` / `technologies` / `consulting` / `studios` 等。

- **漏抽**：既无后缀、也无地址特征的机构名不判公司——这是「无证据不下判」的代价。TC28 的 `Apple` 即属此列，是**已知能力边界**（见 §6.3），也是刻意取舍：宁可漏抽 `Apple`，也不把 `Apple` 误判成地址或姓名。
- **误报**：词表按子串匹配，长词里的片段会命中。代码已刻意避开已知冲突（不收 `co`——它会命中 `Consulting`；不收 `tech`——会命中 `Technical Director`；行业词表不收与职称重叠的 `设计` / `网络`），但这只是逐个排除，新写法仍可能撞上。
- **单字地址特征不再在整词内部生效**：`室` / `号` / `楼` / `层` 只在整词层面成立，`工作室` / `写字楼` 按整词处理，避免「蓝海设计工作室」被单字 `室` 抢成地址。
- **顺序副作用已在本次变更中消除**：改前公司判定早于职位，含机构后缀的部门名会先被占成公司；现在职位前置、且公司与地址共用一次判定，「公司名被误填进地址 / 姓名」的错误已归零（§6.3）。

#### 3.4 职位与部门

职位（2026-11-02 起）改**双路**判定（`isJobTitleLike`）：① **后缀形态路**——整段 2–6 个汉字、全为中日韩字符、不含数字、不含强地址特征与省 / 区 / 县 / 镇 / 乡（**刻意不含「市」**，以免误伤「市场经理」），且以职务后缀（`师` / `员` / `长` / `监` / `理` / `士` / `教练` / `主任` / `总监`…）结尾；② **通用词表路**——中文 47 词与西文职务词，且西文由**子串匹配改为末词去尾标点后整词命中**（`isLatinJobTitleLike`）。

- 后缀路让词表外的常见职务可外推（`摄影师` / `调度员` / `测绘员` / `售票员` / `快递员`），实测职位正确率由 56.7% 升到 93.3%（§6.3）；但表外的**自造职称**（如 `Chief of Staff` 这类既不在词表、也无中文后缀的写法）仍漏抽。
- 标语（`专业可靠`）不含职务后缀、也不命中词表，保持 `nil`，不被误判为职位。
- 段首西文职位词会被拆出来单独判定（`Professor Tongji University` → `Professor` + `Tongji University`），段尾的多词短语整体保留。
- 部门词表含单字 `部` / `处` / `科` / `系`，命中面很宽：含这些字的**地址**（如「解放路 3 号 2 处」）在顺序上已先被地址分支占走，但不含地址特征时仍可能被误判成部门。

#### 3.5 电话三型（手机 / 固话 / 传真）

规则（2026-11-02 起）：值必须「只由数字与 `+ - ( ) . / ·` 与空格组成、数字 7–15 位」。有标签按标签归属；无标签时**形态优先**——`+86` 且 ≥13 位 → 手机、首位 `0` → 固话、≥11 位 → 手机；**形态判不出**（如 `+1-555-0307`）时按「手机 → 固话 → 传真」填**第一个空槽位**（`phoneTargetWithoutLabel(in:fields:)` 读当前 `fields` 快照）；形态能判出但目标槽位**已被占用**时返回 `nil`（**宁漏不假**）。

- **误报**：无标签的传真号（如「021-6000-3001」单独一行）会因 `0` 开头被判固话；形态判不出时按空槽位落位，可能与人工期望的槽位不符——`ground_truth.json` 对同为无标签单行的 `+1-555-XXXX`，在 TC02 / 06 / 10 / 13 / 17 标 **mobile**、在 TC07 / 21 标 **phone**，属**数据集标注内部不一致**（§6.3），解析器按规则落 `mobile` 因而在 TC07 / 21 判为错。
- **漏抽**：全角括号（`（021）…`）不在允许的分隔符内，而归一化不转全角括号，整段判定失败、号码丢失；带分机号（`转 8021`）或含汉字的号码行同样失败。
- **归属冲突的取舍**：同一张名片两个手机号时，第二个形态判为手机而 `mobile` 已占，按「宁漏不假」**留空**而不改投固话。改前是「其余一律落手机」并丢弃后续候选，这在 TC23（三个无标签号码）上表现为固话 / 传真漏抽；改后改为按空槽位落位，TC23 已修好（固话 36.7% → 40.0%、传真 10.0% → 13.3%）。

#### 3.6 邮箱

- 正则 `[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}`：段内含匹配子串即抽该子串，因此「邮箱和其它文字同行」也能抽出。
- 边界：中文域名邮箱、TLD 为单字符的邮箱不匹配；OCR 把 `@` 认成 `(a)` 或把字母认错时无法修复（这一层不做纠错）。

#### 3.7 网址

规则：带 `http(s)://` 或 `www.` 前缀直接认定；否则必须**整段就是域名**（无空格 / 冒号 / 斜杠，且顶级域在 13 个已知 TLD 内）。

- **漏抽**：未知 TLD（`.xyz`、`.tech` 等）不判网址；无协议的带路径写法（`example.com/about`）因含斜杠不判；带标签的整行（`网址:http://a.com`）走标签分支，能正常归属（测试 `testLabeledWebsiteLineIsNotTreatedAsUrl`）。
- **不误报**：段内含 `@` 时直接返回 `nil`，避免把邮箱当网址；`Apple` 这类单词不含点，也不判网址。

#### 3.8 地址与邮编

- 地址（2026-11-02 起）：与公司共用**特征竞争**（见 §3.3）——门牌号类数字或行政区划词是地址侧的证据，公司后缀在段尾是公司侧的证据，都无证据则不下判。强特征（`路` / `街` / `号` / `楼` / `大厦` / `广场` / `street` / `suite`…）与弱特征（`省` / `市` / `区` / `县` / `district` / `city`…）两级词表仍在使用，只抽第一段命中的，**不做多行地址合并**——分两行写的地址只留下第一行。
- 邮编：只认**整段就是 6 位数字**。「邮编：430074」走标签分支可抽出；写进地址行中间（「…大道 100 号 430074」）不会被抽出，会被整段判成地址。

#### 3.9 与规格 4.3 的偏差（需如实记录）

| 规格 4.3 的要求 | 当前实现 | 状态 |
| --- | --- | --- |
| 字段歧义（如 `Apple`）：无法确定则 `nil`，不得多字段重复填充 | 单西文词既不判姓名也不判公司，保持 `nil` | 符合 |
| 人名 vs 公司：禁止把公司名识别为姓名 | 机构后缀优先于姓名判定 | 基本符合，但见 §3.2 的「无后缀机构简称」风险 |
| 多电话必须区分 Mobile / Office / Fax | 有标签时按标签归属；无标签时用启发式 | 符合，标签缺失时可能误归（§3.5） |
| **多 Email：主邮箱入 `email`，其余进入 `notes` 或保留列表** | 主邮箱入 `email`；其余按出现顺序存入 `ExtractedCardFields.additionalEmails`，`makeCard()` 时拼成「其它邮箱：a@b.com、c@d.com」写入 `BusinessCard.notes`（与主邮箱重复的候选不重复收集） | 符合（测试 `testOnlyFirstCandidatePerFieldIsKept` / `testDuplicateEmailIsNotCollectedTwice` / `testAdditionalEmailsAreWrittenIntoNotes`） |
| 中英混排：姓名保留原语言、不翻译 | 保持原文（测试 `testBilingualNameKeepsOriginalLanguage`） | 符合 |
| 字段缺失：返回 `nil`，禁止补全 | 硬约束，由 `makeCard()` 与误报率指标共同守住 | 符合 |

### 4. 检测与校正层对 OCR 的上游影响

这几条严格说属 T06 能力，但它们的误差会直接变成 OCR 的输入误差，故一并汇总：

- **只检矩形**：`VNDetectRectanglesRequest`（`minimumAspectRatio` 0.3、`minimumSize` 0.18、`quadratureTolerance` 30、`maximumObservations` 4、`minimumConfidence` 0.5）。弯曲、被手指遮挡、倾斜过大、白底白桌上的名片可能直接 `notFound`。
- **取面积最大者**：多个候选中挑面积最大的一个。画面里存在更大的矩形（桌面边缘、显示器、另一张纸）时会选错，而选错后走的是「检测成功」路径，不会提醒用户。
- **`isReliable()` 阈值已在真实照片上标定**：面积 `0.12…0.98`、长宽比 `1.15…3.6`，已于 2026-11-03 在 Mac 端人工验收时按真实名片照片完成标定（见 `docs/验证报告.md 附录 A` M18 / M36）。阈值偏严会把正常名片判成「不可靠」（多走一次手动调整），偏松会把桌面误检当名片放过去。
- **不自动转 90°**：竖版名片合法，仅凭四边形比例无法区分「竖版名片」与「照片方向不对」，误转会破坏识别；因此方向问题被推给上游，识别不理想时靠重拍或手动调整。
- **手动调整的取舍**：用户手动改框时**豁免**自动检测的最小面积（0.12）与长宽比启发式（用户已看过照片并自己指出名片位置，再用同一套启发式拒一次会让该功能形同虚设），但**保留面积上限 0.98**，守住规格「不直接把整张图片当作名片」。

### 5. 已明确不做（能力之外）

对齐 `docs/规格说明书.md` 2.2 与作业文档第十五节，以下不在本次复刻范围，也不在本文的能力边界讨论范围内：用户注册 / 会员 / 订阅支付 / 广告、云同步与多设备同步、团队名片库与 CRM（Salesforce）同步、企业权限与组织、数字名片设计 / 模板、QR 名片交换、Email Signature、AI 企业情报 / 公司分析、会议录音与总结、销售漏斗。

在**本工程范围之内**但明确不做的还有：

- 手写体识别、竖排中文专门处理、名片 Logo 与版式的语义理解。

### 6. 如何把上述边界量化（任务 4.4，已于 2026-11-01 实测）

#### 6.1 指标定义（脚本已实现）

`CamCardCloneTests/FieldExtractionEvaluator.swift` 对 `BusinessCardFieldParser` 在 OCR 原文上的输出与 `testcards/ground_truth.json` 比对，输出：

- **字段级准确率** = 判定正确字段数 / 参与评价字段数；
- **缺失字段误报率** = 本应为空却抽出值的字段数 / 本应为空的字段数（量化「不得虚构」，理想值为 0）；
- 逐字段的正确 / 参与数与**错误明细表**（名片 ID、字段、判定、真值、抽取结果），用于定位是哪些字段在拉低准确率。

判定分五种：`correct` / `mismatch`（抽成了别的）/ `missed`（漏抽）/ `invented`（虚构）/ `absent`（本应为空且确实为空）。比对前做既定的等价归一化：去首尾空白、压缩内部空白、忽略大小写；电话类字段再忽略分隔符（`138-0000-0001` 与 `13800000001` 视为相同）。参与评价的字段为 9 个：姓名 / 公司 / 职位 / 手机 / 固话 / 传真 / 邮箱 / 网站 / 地址——**邮编与部门不在评价范围内**，数据集里的 `additionalEmails` 也不参与评价（评价键取自 `groundTruth` 与 `expectedAbsent`）。

#### 6.2 数据补齐与执行（已于 2026-11-01 完成）

原有两处缺口均已补齐：

1. **OCR 原文**：在物理 Mac（`iPhone 17` / iOS 27.0 模拟器）上以 `TEST_RUNNER_EXPORT_OCR_TEXT=1` 跑 `OCRTextCorpusExporterTests`，产出 `testcards/ocr/TC01–TC30.txt`（30/30，`** TEST SUCCEEDED **`）；
2. **名片图片**：`testcards/images/TC01–TC30.png`（按真值逐字渲染的 30 张合成名片，生成脚本 `testcards/tools/generate_card_images.py`）。

随后 `testFieldAccuracyOnCorpusIsPendingUntilOCRTextsExist` 由 `XCTSkip` **转为真跑**（`Executed 12 tests, with 0 failures`），由 `FieldExtractionEvaluator.report` 生成准确率、误报率与错误明细。**补充**：下述数字基于合成图整图识别；用**真实名片照片**走一遍 App 识别链路（`docs/验证报告.md 附录 A` M18）的复核已于 2026-11-03 在 Mac 端完成。

#### 6.3 实测结果

**改规则前（2026-11-01，Mac 本机，`fix-field-classification-errors` 提案之前）**：30 张 / 270 个字段，整体「正确」**51.9%（140/270）**、误报率 **3.8%（4/105）**，错误明细 29 条；逐字段：姓名 96.7% / 公司 76.7% / 职位 56.7% / 手机 76.7% / 固话 36.7% / 传真 10.0% / 邮箱 63.3% / 网站 16.7% / 地址 33.3%。证据：`docs/evidence/mac-2026-11-01/mac-field-accuracy.log`。

**改规则后（2026-11-02，CI，提交 `d74450e`，check-run `125116046722`）**：整体「正确」**57.8%（156/270）**、误报率 **1.9%（2/105）**，错误明细减到 **11 条**；逐字段：姓名 96.7% / 公司 83.3% / 职位 **93.3%** / 手机 76.7% / 固话 40.0% / 传真 13.3% / 邮箱 63.3% / 网站 16.7% / 地址 36.7%。证据：`docs/evidence/ci-2026-11-02/field-accuracy-report.md`（经免登录的 `check-runs/125116046722/annotations` 读回，报告行以 `FIELDRPT` 前缀分块发出）。

- **读数口径（不变）**：270 个字段里 105 个「本应为空」按判定口径永不计入「正确」，理论天花板只有 165/270 = **61.1%**，故 57.8% 不是失败率；在确有值的 165 个字段上抽取成功率由改前 140/165 ≈ 84.8% 升到 **156/165 ≈ 94.5%**。
- **两类归零**：改前 29 条错误中的「**字段归属错**」（首行公司名被误填进地址 / 姓名）与「**职位召回缺失 / 截断**」两类在改后**全部消失**——职位 56.7% → 93.3%、公司 76.7% → 83.3%、地址 33.3% → 36.7%；TC23 的固话 / 传真漏抽也一并修好（固话 36.7% → 40.0%、传真 10.0% → 13.3%）。修法见 §3.3 / §3.4 / §3.5。
- **剩余 11 条按三类归因（如实记录；未达「`invented` 归零」）**：
  1. **数据集标注内部不一致，4 条（非规则缺陷）**：TC07 与 TC21 各「手机 `invented` + 固话 `missed`」。同为无标签单行 `+1-555-XXXX`，`ground_truth.json` 在 TC02 / 06 / 10 / 13 / 17 标 **mobile**、在 TC07 / 21 标 **phone**。解析器按「形态判不出 → 首个空槽位」落 `mobile`，与后两张真值不符；经用户拍板**不改数据集**，记为已知残留，故电话类错误由 6 条减到 4 条而**不归零**。
  2. **OCR 噪声，6 条**：TC12 邮箱 `david@abc.example.edu → …eau`（`edu→eau`）、TC13 公司 `Global Vision Ltd. → Lta.`（导致公司漏抽、且该段无公司证据后落到姓名判定，连带 TC13 姓名 `mismatch`）、TC15 公司 `康泰医疗器械 → 嚣械`、TC20 与 TC26 的邮箱因 OCR 原文含空格而不匹配。这些属 OCR 层质量（§2），不在字段抽取规则范围内。
  3. **能力边界，1 条（刻意取舍）**：TC28 公司 `Apple` 漏抽——既无公司后缀、也无地址特征，按 D1「无证据不下判」保持 `nil`（§3.3）。宁可漏抽 `Apple` 也不把 `Apple` 误判成地址 / 姓名，未违反「缺失字段返回 nil，严禁虚构数据」的硬约束。
- **`invented` 的变化**：由 4 降为 **2**（不是 0），剩余 2 条即上述 TC07 / TC21 的「号码归错槽」。改前 4 条 `invented` 经取证均为「归错桶」（公司名被误填进地址 / 姓名，或无标签号码归错槽），此轮修复后**不再出现公司名误入地址 / 姓名**的那一类，只剩电话类 2 条。填的文本都真实存在于名片上，属**分类准确率**问题，未违反「缺失字段返回 nil，严禁虚构数据」的硬约束。
- **读数口径（不变）**：数值基于**合成图整图识别**（不经检测与透视校正）；真实名片照片上的准确率已于 2026-11-03 在 Mac 端人工验收通过（§7）。
